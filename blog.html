Building a Serverless Resume on AWS

Dubari Kalita 7 Phases ~20 Hours Cloud Resume Challenge

Instead of putting my resume on GitHub Pages or a PDF link, I decided to build and host it the way a cloud engineer actually would — using AWS, serverless architecture, infrastructure as code, and a fully automated CI/CD pipeline. Here's exactly what I built, how it works, and what I learned.

01 What Is This Project

The Serverless Resume Platform is a personal resume and portfolio website that demonstrates practical cloud and DevOps skills by using those very skills to build and deploy itself. The site is a static HTML/CSS/JS page hosted on AWS, with a real serverless backend that tracks and displays a live visitor counter.

Every part of this project — from where the files are stored, to how they get deployed — uses production-grade AWS services and practices. Nothing is click-ops. Everything is automated or defined as code.

The core idea

The resume itself is proof of the skills listed on it. A visitor can read "GitHub Actions CI/CD" on the page and know the page was deployed using exactly that.

02 How It Works

The project is split into two separate repositories — frontend and backend — each with its own automated deployment pipeline.

FRONTEND ───────────────────────────────────────── Browser → CloudFront (HTTPS + CDN) → S3 (private) ↑ Custom domain via Route 53 + ACM SSL BACKEND — visitor counter ───────────────────────────────────────── JS fetch(POST) → API Gateway → Lambda (Python) ↓ DynamoDB { visitor_count + 1 } ↓ returns { "count": N } CI/CD ───────────────────────────────────────── git push → GitHub Actions ├── Frontend: s3 sync + CloudFront invalidation └── Backend: pytest gate → sam build → sam deploy

The visitor counter is the interesting part. When the page loads, a JavaScript fetch() call hits the API Gateway endpoint. API Gateway triggers a Python Lambda function, which runs an atomic ADD on a DynamoDB item — incrementing the count with no race conditions — and returns the new value as JSON. No database is ever exposed directly to the public.

03 The 7 Phases

I broke the project into 7 sequential phases so there was always a working state at every step.

1
Frontend — HTML / CSS / JS
Built the resume page locally. Designed the theme, structure, and the visitor counter UI placeholder.
2
AWS Setup + S3 Static Hosting
Created S3 bucket, configured static website hosting, uploaded files, set bucket policy for public read.
3
CloudFront + HTTPS
Put CloudFront in front of S3. Added Origin Access Control, free ACM SSL certificate, CloudFront-only bucket policy.
4
DynamoDB + Python Lambda
Created DynamoDB table, wrote Python Lambda with atomic counter increment, wrote unit tests with mocked AWS calls.
5
API Gateway
Exposed Lambda as a public REST API. Configured CORS preflight (OPTIONS) so the browser allows cross-origin calls.
6
Infrastructure as Code — AWS SAM
Replaced all manual CLI commands with a single template.yaml. sam deploy now recreates the entire backend from scratch.
7
GitHub Actions CI/CD
Two automated pipelines. Frontend: push → S3 sync → CloudFront invalidation. Backend: push → pytest gate → SAM deploy.

04 The Parts That Tripped Me Up

CORS — the silent killer

CORS caused more debugging time than anything else. The browser sends an HTTP OPTIONS preflight request before the actual POST — asking "are you going to allow this?". If API Gateway doesn't handle OPTIONS and return the right headers, the browser silently blocks the real request. The fix was adding a MOCK integration for OPTIONS that returns the correct Access-Control-Allow-* headers.

boto3 at module level breaks pytest

My first version of counter.py initialised boto3.resource("dynamodb") at the top of the file. This meant when pytest imported the file, it immediately tried to connect to AWS and failed with NoRegionError. The fix was moving boto3 initialisation inside the handler function so it only runs on actual invocation, not on import.

SAM vs manually created resources

When I introduced SAM in Phase 6, it tried to create resources with the same names as ones I'd manually created earlier — failing with "resource already exists". The lesson: use IaC from the very beginning, or cleanly delete manually created resources before handing ownership to SAM.

Key insight

CloudFormation maintains state of every resource it manages. If you create something manually outside of it, CloudFormation doesn't know it exists and will conflict with it. Always let your IaC tool own everything it touches.

05 What I Learned

  • IAM roles vs IAM users — Lambda doesn't use access keys. It assumes an IAM role at runtime. Understanding identity-based vs resource-based policies was a foundational shift in how I think about AWS permissions.
  • IaC is not optional — Manually created resources are invisible to version control. You can't review, audit, or reproduce them. After going through the pain of recreating everything in SAM, I now treat IaC as a non-negotiable starting point.
  • Test-gated CI/CD is genuinely useful — Having pytest block the SAM deploy when a test fails saved me from deploying broken code twice during this project. The pipeline becomes a safety net, not just automation.
  • CloudFront caching catches you off guard — After every frontend change, the old cached version kept showing. Cache invalidation is a real operational concern. Automating it in GitHub Actions was the right call.
  • Two repos, two pipelines is the right separation — Keeping frontend and backend separate means a CSS change doesn't trigger a SAM deploy, and a Lambda fix doesn't invalidate CloudFront unnecessarily. Separation of concerns applies to repositories too.
